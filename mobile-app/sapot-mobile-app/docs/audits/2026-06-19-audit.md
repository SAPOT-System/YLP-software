## 1. Duplicate Components

### 1.1 `PrimaryButton` and `SecondaryButton` are near-identical
**Files:**
- `features/auth/components/primary-button.tsx`
- `features/auth/components/secondary-button.tsx`

**Description:** These two components are structurally identical — same props interface (only name differs), same `useThrottledPress` wiring, same `StyleSheet`, same log prefix convention. The only difference is `mode="contained"` vs `mode="outlined"`. A single `AuthButton` with a `variant` prop would replace both.

**Severity: MEDIUM**

---

### 1.2 `VerificationCodeModal` and `VerificationCodeContent` duplicate OTP logic
**Files:**
- `features/settings/components/verification-code-modal.tsx` (263 lines)
- `features/settings/components/verification-code-content.tsx` (242 lines)

**Description:** Both components implement the exact same OTP entry flow: `CODE_LENGTH = 6`, `OTP_TTL_SECONDS = 300`, `RESEND_COOLDOWN = 60`, the same countdown timer `useEffect`, the same resend-cooldown `useEffect`, identical `isVerifying`/`resendConfirmed`/`resendCooldown` state, and equivalent slot-size math. The only structural difference is that `VerificationCodeModal` wraps the content in a `<Portal><Modal>`. `VerificationCodeContent` should be extracted as the inner content and `VerificationCodeModal` should compose it.

**Severity: HIGH** (505 lines of nearly-duplicated logic)

---

### 1.3 `AuthTextInput` and `SettingsTextInput` duplicate the labeled text-input pattern
**Files:**
- `features/auth/components/auth-text-input.tsx`
- `features/settings/components/settings-text-input.tsx`

**Description:** Both render a label + `<TextInput mode="outlined" outlineStyle={{ borderRadius: 10 }}>` + optional trailing icon with the same prop shape (`label`, `placeholder`, `value`, `onChangeText`, `error`, `required`). The settings variant adds `labelRight` and `checkIcon`, while the auth variant adds a password-toggle. A single shared `AppTextInput` in `features/shared/components/` with optional `variant` or composable extension would eliminate both.

**Severity: MEDIUM**

## 2. Duplicate Hooks

### 2.1 `useEmailReset` and `useSmsReset` duplicate the send-code / verify-code / lockout pattern
**Files:**
- `features/auth/hooks/use-email-reset.ts`
- `features/auth/hooks/use-sms-reset.ts`

**Description:** Both hooks contain:
- An identical `parseDetail` helper function (lines 9–15 in each file — word-for-word identical)
- The same state shape: `isLoading`, `error`, `isCodeSent`, `attemptsRemaining` plus `lockout = useLockoutTimer(...)`
- Parallel `sendCode` and `verifyCode` functions with the same try/catch structure, same 400/429 branching, same `lockout.setLock` / `lockout.clearLock` calls
- A `reset()` function resetting the same fields

The only substantive difference is the API endpoint called and the identifier field (`email` vs `phone`). A single generic `useCodeReset(config)` hook would handle both, with `parseDetail` extracted to `features/auth/utils/`.

**Severity: HIGH**

---

### 2.2 `useVerifyQuestion` and `useVerifyRecoveryKey` duplicate the 429-lockout verify pattern
**Files:**
- `features/auth/hooks/use-verify-question.ts`
- `features/auth/hooks/use-verify-recovery-key.ts`

**Description:** Both hooks share the same `parseDetail` helper (copy-pasted identically in `use-verify-recovery-key.ts` and also duplicated from the two hooks above — that's 3 copies of `parseDetail` across 3 files). They share the same pattern: `lockout.isLocked` guard → API call → `lockout.clearLock()` on success → 429 dispatch to `lockout.setLock()` → 400 dispatch to `parseDetail`. The only differences are the API called and the field name in the error object.

**Severity: HIGH** (including `parseDetail` appears 3× across: `use-email-reset.ts`, `use-sms-reset.ts`, `use-verify-recovery-key.ts`)

---

### 2.3 GPS hooks use camelCase filenames while all other hooks use kebab-case
**Files:**
- `features/gps/hooks/useGpsHistory.ts`
- `features/gps/hooks/useGpsStreaming.ts`
- `features/gps/hooks/useLatestLocations.ts`
- `features/gps/hooks/useLocationPermission.ts`

**Description:** All other hooks across all features consistently use kebab-case filenames (e.g., `use-chat-service.ts`, `use-auth-container.ts`). These four GPS hooks use camelCase filenames. While not a runtime defect, this breaks naming convention consistency and makes `find`/`grep` patterns less predictable.

**Severity: LOW**

---

### 2.4 `useAnnouncements` called twice per render tree
**Files:**
- `features/announcements/components/announcement-list-row.tsx`
- `app/(drawer)/announcements.tsx`

**Description:** `AnnouncementListRow` is rendered inside the `announcements.tsx` screen, which already calls `useAnnouncements()`. The component then calls `useAnnouncements()` again independently to get the count for the badge. React Query deduplicates the network request, but the hook still runs twice per render cycle. The `data` should be passed as a prop to `AnnouncementListRow` from the parent screen.

**Severity: LOW**

## 3. Duplicate Services / Utilities

### 3.1 `formatRelativeTime` duplicated across GPS and shared utils
**Files:**
- `features/gps/utils/format-relative-time.ts` (accepts `string` only)
- `features/shared/utils/format-relative-time.ts` (accepts `number | string`, includes input guard)

**Description:** Both export a `formatRelativeTime` function with the same `s/m/h/d ago` logic. The shared version is strictly more capable (accepts epoch ms, has `Number.isFinite` guard). The GPS version should be deleted and its single caller (`features/gps/components/UserMarkerSheet.tsx`) should import from `@/features/shared`.

**Severity: MEDIUM**

---

### 3.2 `tcp-encryption.ts` and `ws-encryption.ts` duplicate the NaCl box + base64 pattern
**Files:**
- `features/shared/services/tcp-encryption.ts`
- `features/shared/services/ws-encryption.ts`

**Description:** Both files import `nacl`, `encodeBase64`, `decodeBase64` and implement `nacl.randomBytes(nacl.box.nonceLength)` → `encodeBase64(nonce)` + `encodeBase64(ciphertext)` for encryption, and `decodeBase64` → `nacl.secretbox.open` / `nacl.box.open` for decryption. The envelope shapes (`{ nonce, box }`) are identical. Low-level helpers like `generateNonce`, `encodeEnvelope`, and `decodeEnvelope` could be shared in a `nacl-utils.ts` module. Currently the duplication is tolerable because the two files serve different transport concerns, but the risk of divergence is real.

**Severity: LOW**

---

### 3.3 `parseDetail` utility duplicated across 3 auth hook files
**Files:**
- `features/auth/hooks/use-email-reset.ts` (lines 12–17)
- `features/auth/hooks/use-sms-reset.ts` (lines 9–15)
- `features/auth/hooks/use-verify-recovery-key.ts` (lines 9–15)

**Description:** The identical private function `parseDetail(detail: unknown): { message: string; attemptsRemaining: number | null }` appears three times. It should be extracted to `features/auth/utils/` and imported where needed.

**Severity: MEDIUM**

## 4. Architecture Violations

### 4.1 `sync-service.ts` imports chat repositories directly, bypassing `features/chat` index
**File:** `features/sync/services/sync-service.ts` (lines 22–26)

```ts
import type { MessageReceiptManager } from "@/features/chat/services/message-receipt-manager";
import { ConversationParticipantRepository } from "@/features/chat/repositories/conversation-participant-repository";
import type { MessageRepository } from "@/features/chat/repositories/message-repository";
```

**Description:** These are direct deep imports into `features/chat/` internals. `features/chat/index.ts` already re-exports all three of these. The imports should use `@/features/chat` (the public index), not the internal paths.

**Severity: MEDIUM**

---

### 4.2 App screens import auth API functions directly, bypassing feature index
**Files:**
- `app/auth/forgot-password/recovery-key-reset.tsx` — imports from `@/features/auth/api/auth.api`
- `app/auth/forgot-password/enter-identifier.tsx` — same
- `app/(drawer)/settings/account/generate-recovery-key.tsx` — imports from `@/features/auth/api/auth.api`
- `app/(drawer)/settings/account/security-question.tsx` — imports from `@/features/auth/api/auth.api`
- `app/(drawer)/settings/account/change-password.tsx` — imports from `@/features/auth/api/auth.api`
- `app/auth/login/server-login.tsx` — imports from `@/features/auth/hooks/use-lockout-timer`
- `app/(drawer)/settings/account/authenticate.tsx` — imports from `@/features/auth/utils/validation`

**Description:** Multiple screen files bypass `features/auth/index.ts` and reach directly into internal subfolders (`/api/`, `/hooks/`, `/utils/`). `features/auth/index.ts` exports all of these, so the fix is to change each import to `@/features/auth`.

**Severity: MEDIUM**

---

### 4.3 `call-context.tsx` contains navigation logic
**File:** `features/call/context/call-context.tsx` (lines 10, 99, 147, 152, 155)

**Description:** The call context performs `router.replace("/(drawer)/(tabs)")` and `router.replace({...})` to navigate on call-end events. Navigation imperative calls belong in `app/` screens or should be expressed as callbacks passed from screens to contexts. Hardcoding routes in a feature context couples the feature to the app's navigation structure.

**Severity: MEDIUM**

---

### 4.4 `call-banner.tsx` performs navigation (`router.push`)
**File:** `features/call/components/call-banner.tsx` (lines 101, 141)

**Description:** The banner component imports `useRouter` and calls `router.push(...)` when the user taps it. Route-push logic in a reusable component couples it to the specific route path. The push should be exposed as an `onPress` prop delegated to the parent screen.

**Severity: LOW**

---

### 4.5 `chat-list.tsx` component contains direct WatermelonDB queries
**File:** `features/chat/component/chat-list.tsx` (lines 30–113)

**Description:** `enhanceChats` and `enhanceChat` use `withObservables` with raw `Q.where(...)` / `Q.sortBy(...)` / `Q.take(...)` queries directly in the component file. This is database access that should live in a repository method. The `ConversationRepository` or `MessageRepository` could expose observable queries, keeping component files free of WatermelonDB internals.

**Severity: MEDIUM**

---

### 4.6 `message-list.tsx` component contains direct WatermelonDB queries
**File:** `features/chat/component/message-list.tsx` (lines 31–119)

**Description:** Same issue as 4.5 — `enhanceMessages` and `enhanceMessage` use `withObservables` + `Q` queries inline. Multiple relationship queries (sender peer, message receipts, linked messages) are expressed directly in the component.

**Severity: MEDIUM**

---

### 4.7 `chat-service.ts` performs `database.write()` directly (9 call sites)
**File:** `features/chat/services/chat-service.ts` (lines 509, 832, 1016, 1050, 1151, 1208, 1353, 1639)

**Description:** The service bypasses repositories to call `database.write()` directly at multiple points (creating messages, conversations, message receipts, and updating conversation state). Per the architecture, WatermelonDB writes should go through repositories. This makes the service hard to test in isolation and means write logic is split across service and repository layers.

**Severity: HIGH**

---

### 4.8 `useGpsStreaming` instantiates `GpsLocationService` directly with `new`
**File:** `features/gps/hooks/useGpsStreaming.ts` (line 8)

```ts
const service = useRef(new GpsLocationService());
```

**Description:** The hook creates a service instance directly, bypassing the DI container. `GpsLocationService` is outside `MainContainer` wiring, making it impossible to swap it in tests without module-level mocking. This is flagged in CLAUDE.md as a violation: "Services are not singletons — instantiated once in `MainContainer` and passed down via React context." GPS is the only feature that works this way.

**Severity: MEDIUM**

## Recommendations

### Priority 1 — High severity, actionable immediately

1. **Extract `parseDetail` to `features/auth/utils/`** — one change per file, eliminates 3 copies.
2. **Consolidate `useEmailReset` / `useSmsReset` into `useCodeReset(config)`** — reduces ~200 lines to ~100 + a config object.
3. **Delete `features/gps/utils/format-relative-time.ts`** — update the one import in `UserMarkerSheet.tsx` to use `@/features/shared`.
4. **Resolve `VerificationCodeModal` / `VerificationCodeContent` duplication** — delete the modal wrapper or wire it as a thin shell around the content component.
5. **Route all `chat-service.ts` `database.write()` calls through repositories** — biggest architecture violation, directly affects testability.
6. **Fix 7 screen files that bypass `features/auth/index.ts`** — change deep imports to `@/features/auth`.
7. **Fix `sync-service.ts` direct chat repo imports** — use `@/features/chat` public index.

### Priority 2 — Medium severity, plan for next sprint

8. **Decompose `chat-service.ts` (1,650 lines)** into `MessagePersistenceService`, `MessageSendService`, `ConversationService`.
9. **Decompose `connection-service.ts` (1,407 lines)** — split `connectToPeer` (293 lines) into `initiateTcpConnection`, `handleSignalingHandshake`, `setupDataChannels`, etc.
10. **Move `GpsLocationService` into `MainContainer` wiring** — inject via context, remove `new GpsLocationService()` in `useGpsStreaming`.
11. **Rename GPS hook files to kebab-case** to match codebase convention.
12. **Move `chat-list.tsx` / `message-list.tsx` WatermelonDB queries** into repository observable methods.
13. **Extract navigation callbacks** from `call-context.tsx` and `call-banner.tsx` into props injected by parent screens.

### Priority 3 — Low severity / housekeeping

14. Remove commented-out `// label={label}` from `settings-text-input.tsx`.
15. Replace hardcoded `host: "192.168.1.17"` in `reactotron.ts` with `EXPO_PUBLIC_REACTOTRON_HOST`.
16. Create shared `AppTextInput` in `features/shared/components/` to unify `AuthTextInput` and `SettingsTextInput`.
17. Merge `PrimaryButton` / `SecondaryButton` into a single `AuthButton` with a `variant` prop.
18. Ensure `useLockoutTimer` is re-exported from `features/auth/index.ts` so screens do not need to deep-import it.
