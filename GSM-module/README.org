* Goal

Build a layered SMS relay system using:

#+begin_example
Phone <-> GSM Module <-> Arduino <-> USB Serial <-> FastAPI (GSM Service)
                                                    ↓
                                             FastAPI (Main API)
                                                    ↓
                                              SAPOT System
#+end_example

The system should:

1. Receive SMS messages
2. Forward SMS data to the GSM FastAPI service
3. Let the main FastAPI application decide responses
4. Send SMS replies back through the GSM module
5. Support SAPOT SMS relay workflows
6. Keep GSM handling isolated from application/business logic

---

* Updated Architecture Decision

Chosen Architecture:
Thin Arduino + Dedicated GSM FastAPI Service

#+begin_example
Phone
  ↓
GSM Module
  ↓
Arduino (bridge only)
  ↓
FastAPI GSM Service
  ↓
FastAPI Main API
  ↓
SAPOT Application Logic
#+end_example

This separates:

- hardware communication
- SMS transport
- business logic
- user/session management

into independent layers.

---

* High-Level Service Roles

** Arduino Layer

Purpose:
Hardware bridge and GSM watchdog.

Responsibilities:
- communicate with GSM module
- detect GSM failures
- auto-reset GSM module when needed
- extract SMS metadata
- forward events to GSM FastAPI service
- execute outgoing SMS commands

Arduino SHOULD NOT:
- contain business logic
- know SAPOT workflows
- validate users
- store sessions
- understand commands semantically

Arduino must remain generic and reusable.

---

** FastAPI GSM Service

Purpose:
Serial communication gateway between Arduino and backend services.

Responsibilities:
- maintain serial connection with Arduino
- parse serial protocol
- expose HTTP/WebSocket API
- relay events to main FastAPI service
- receive SMS send requests
- queue outgoing GSM commands
- centralize GSM logging
- monitor modem health

This service acts as a transport layer.

---

** FastAPI Main Service

Purpose:
Application brain and SAPOT backend.

Responsibilities:
- parse incoming SMS meaning
- manage SMS user sessions
- validate users against SAPOT database
- route SMS messages
- generate responses
- maintain conversation state
- authenticate requests
- integrate with SAPOT mobile/web app
- database integration
- future dashboard/admin integration

The main FastAPI service owns ALL business logic.

* Communication Layers

There are now THREE communication layers.

---

** Layer 1: GSM ↔ Arduino

Protocol:
AT commands

Example:

#+begin_example
+CMT: "+639171234567","","26/05/07,10:30:00+32"
HELLO
#+end_example

Controlled entirely by the GSM modem.

---

** Layer 2: Arduino ↔ FastAPI GSM Service

Transport:
USB serial

Protocol:
Custom line-based protocol

Requirements:
- one message per line
- machine-readable
- predictable
- easy to debug

Format:

#+begin_example
EVENT|DATA|DATA
#+end_example

---

** Layer 3: GSM FastAPI ↔ Main FastAPI

Transport:
HTTP REST API or WebSocket

Recommended:
HTTP for MVP

Example flow:

#+begin_src json
POST /sms/incoming
{
  "sender": "+639171234567",
  "message": "PING"
}
#+end_src

Main API response:

#+begin_src json
{
  "reply": "PONG"
}
#+end_src

Then GSM service sends:

#+begin_example
SEND_SMS|+639171234567|PONG
#+end_example

to Arduino.

* SMS Session Strategy

Unlike simple command parsing, SAPOT requires session-based SMS flows.

Each phone number should maintain a session state.

Example:

#+begin_src json
{
  "+639171234567": {
    "target": "+639998887777",
    "state": "CONNECTED"
  }
}
#+end_src

This state SHOULD exist only in the Main FastAPI service.

Arduino and GSM FastAPI remain stateless.

---

* SAPOT SMS Relay Workflow

** Step 1 — User Sends Initial Message

#+begin_example
hi there sapot server
#+end_example

---

** Step 2 — Main API Creates Session

Server responds:

#+begin_example
Hi! Welcome to SAPOT SMS relay feature.

Please enter your target recipient using:

[target] +639123456789
#+end_example

Session state:

#+begin_example
WAITING_FOR_TARGET
#+end_example

---

** Step 3 — User Sends Target

#+begin_example
[target] +639124323459
#+end_example

Main API behavior:
- validate target number
- check SAPOT database
- store target in session

---

** Step 4A — Target Exists

Response:

#+begin_example
Your message was forwarded to <username>
through both SMS and the SAPOT app.

The user may or may not reply.
#+end_example

Session becomes:

#+begin_example
CONNECTED
#+end_example

---

** Step 4B — Target Does Not Exist

#+begin_example
This user does not exist within the SAPOT database.

Please enter a valid number.
#+end_example

Session resets to:

#+begin_example
WAITING_FOR_TARGET
#+end_example

---

* Persistent SMS Relay Behavior

After a successful target selection:

#+begin_example
hello
how are you
good morning
#+end_example

should automatically relay to the selected target.

The target remains active until:
- user changes target
- session expires
- user sends reset command

Example reset command:

#+begin_example
RESET
#+end_example

---

* Suggested SMS Commands

#+begin_example
[target] +639123456789
RESET
HELP
STATUS
#+end_example

Avoid natural language parsing for control commands.

Structured commands are:
- deterministic
- easier to maintain
- safer
- scalable

* Suggested Session State Machine

#+begin_example

    ↓
WAITING_FOR_TARGET
    ↓
CONNECTED
    ↓
RESET
    ↓
WAITING_FOR_TARGET
#+end_example

* Core Architectural Principle

Keep Arduino:
- dumb
- stateless
- hardware-focused

Keep GSM FastAPI:
- transport-focused
- isolated from business logic
- reusable

Keep Main FastAPI:
- smart
- stateful
- responsible for all SAPOT logic

This architecture enables future upgrades:
- dashboards
- cloud deployment
- Redis queues
- WebSocket live monitoring
- PostgreSQL
- async workers
- multi-modem scaling
- distributed GSM gateways
